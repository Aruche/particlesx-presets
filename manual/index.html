Elsewhere

  • Preset catalogue

ParticlesX is a particle emitter for Construct 3. You give it one image, set a few properties, and it produces effects like fire, smoke, sparks, rain and explosions. All of an emitter's particles are drawn as a single batch, so you can run a lot of them without slowing the game down.

Everything has a sensible default: drop one in a layout, set the particle image, and you already have a working effect.

Getting started

  1. Insert ParticlesX into a layout from the General category. The object itself is invisible; you only see its particles. It comes with a soft round dot as its default image, so it already looks like an effect as soon as it is placed.
  2. In the Properties bar, click Image → Edit to replace that image with your own. A soft round dot works for almost everything, and Effect scale is worth knowing about early: it sizes the whole effect in one number.
  3. Set Capacity, Emission rate and Lifetime first. The rest already has usable values.
  4. In the Layout Editor, the emitter draws a small preview of where particles come from, which way they travel and how far they spread. It is a diagram, not a simulation, and it costs nothing at runtime.
  5. Press Preview to test. If the effect needs to react during the game, use the actions and expressions described further down.

Key ideas

Base value plus variation. Most properties come in pairs, such as Start size and Start size variation, or Speed and Speed variation. The first is the base value and the second is how much it randomly differs per particle. With speed 100 and variation 40, each particle gets a random speed between 60 and 140. Set the variation to 0 for identical particles.

One image, drawn in one batch. The emitter does not create Sprite objects. It draws every particle in a single mesh, which is why Capacity is the main performance setting: the mesh is built once, and particles are reused as they expire.

Tint, not colour. Tints multiply with the particle image, so they can colour an image but cannot make it brighter than the image already is. A mostly white, light image tints most predictably. The object's blend mode still applies as usual: switch the emitter to Additive to make particles glow and brighten each other. For fading particles in and out, use the Particle Opacity group rather than the tint alpha, which is ignored.

Relative and World space. In Relative space, particles belong to the emitter: if the emitter moves or rotates, its particles go with it. In World space, particles are left behind where they were emitted, and the emitter simply stops adding new ones there. Gravity keeps pulling the same way in the layout in both cases, so sparks always fall downwards.

The emitter's own angle counts. Rotating the object in the Layout Editor rotates the emission direction, the emission area and the particles' own rotation as well. That makes it easy to aim an effect such as a muzzle flash by rotating the object.

Easing option boxes. Wherever you see an easing property, the same list is used: Linear, Ease in / out / in-out (Quad), Ease in / out / in-out (Cubic), Ease out (Back), Ease out (Bounce) and Ease out (Elastic). Linear moves at a constant rate; the others start slowly, finish slowly, overshoot, bounce or spring, and are the quickest way to make a size or speed change feel natural.

The emitter grows to fit. Particles can travel far from the emitter, so the object automatically expands its bounding box to cover them. You do not need to resize anything to stop particles being culled at the edge of the screen. This means the object's size and origin belong to the plugin while it has particles: do not animate or set the emitter's Width, Height or origin at runtime, because the plugin resets them on the next tick. Set Effect scale to size the effect instead.

Simulation is frame-rate independent. Particle motion is calculated from the time that has passed rather than per frame, so effects look the same at 30, 60 or 144 FPS.

The emission cycle. An emitter goes through a simple cycle: it starts (waiting for the Start delay first, if one is set), emits particles for as long as you ask (Emission duration, where 0 means forever), then stops. Stopping never kills particles that are already alive: they finish their own lifetime and fade out normally. Both timings follow the game's time scale, so pausing the game pauses them.

One scale for the whole effect. Effect scale multiplies every distance and speed in the effect at once, so a preset can be designed once and re-used at whatever size a game needs — a small firework for a handheld screen, a huge one for a boss attack. It changes only the scale, never the timing: the effect looks like the same effect, just bigger or smaller.

Timelines can animate most of the numeric properties. Emission rate, speeds, gravity, direction and spread, sizes, opacity, rotation, tints, the emission area and the timing values can all be animated with a timeline, and the Layout Editor preview follows what the timeline is doing. Structural settings cannot be animated — capacity, the object picks, and every option box, checkbox and text property — so a timeline can never put the emitter into a state it was not built for. Animated values are in the same units the properties use, and Effect scale still applies on top.

Timelines can drive a property two ways: setting it outright, or offsetting it from what it currently is, which is what a timeline's relative tracks do. Both are supported, so keyframes work whether a track is relative or absolute, and the effect keeps running while it is animated.

Started and finished are different questions. Is started tells you whether the emitter is still going to produce particles, which includes its start delay and its emission duration. To ask "is anything on screen", use the ActiveCount expression or the Has particles condition, and use the On all particles dead trigger to know when the last one has gone.

Looping over particles. For each particle runs the rest of the event once for each particle that was alive when the loop started, which is how gameplay can look at individual particles. Inside the loop, ParticleX and ParticleY give the current particle's position in layout co-ordinates, ready to create an object there or measure a distance to it. Particles emitted during the loop are not included, and particles that expire or are removed during the loop are still visited, so the loop always runs as many times as it started with. Remove current particle deletes the particle the loop is on, which is how effects like burning away or absorbing particles are built.

Properties

Properties

PropertyDefaultWhat it does
ImageSoft round dotThe image used for every particle. Click Edit to change it. The default is a 128×128 white radial gradient with transparent padding, so a particle's visible glow is about 70% of its Start size — set Start size around 1.4 times the glow you want.
Effect scale1Scales the whole effect. 2 makes it twice as large and twice as fast, 0.5 halves it.

Most numeric properties can be animated with a Construct timeline: emission rate, the emission area and its angle, lifetime, speeds and their variations, direction, spread, turn speed, gravity and its angle, drag, turbulence and its scale, tints, sizes, opacity, rotation, frame rate, spawn chance and chain decay — plus Effect scale itself. Capacity, object picks, and every option box, checkbox and text property cannot be animated, because changing them while the effect is running would break it.

Effect scale details: it multiplies every distance and speed — particle sizes, speeds and the end speed, the speed bump, gravity, the emission area, and the turbulence swirl size. Lifetime, emission rate, angles, opacity and the turbulence percentage are deliberately left alone, so a scaled effect behaves the same way, just bigger or smaller. Particle density is preserved automatically, because each particle covers more area when it gets bigger. Property values stay in their own units, so they are multiplied by this scale: a speed of 200 on a 2× effect moves particles at 400 pixels per second. Objects created by Spawn object and Spawn on collision are not scaled, since they are your objects.

Particle Lifecycle

What happens where particles end their life, and when the emitter itself finishes.

PropertyDefaultWhat it does
Spawn objectNoneObject type to create where each particle dies, at the particle's position. A family can be picked instead, in which case one of its object types is chosen at random for each spawn. Useful for chain effects such as explosions leaving debris.
Spawn chance100%Percentage of dead particles that spawn the object.
Chain decay100%Reduces the spawn chance of emitters this one creates, so chains fade out instead of running away. Each generation multiplies the chance by this again.
Destroy when finishedYesDestroys the emitter as soon as it stops emitting and its last particle dies, so one-off effects like impacts and explosions clean themselves up.

Chain decay details: it only affects ParticlesX emitters that this emitter creates, whether on death or on collision. The first generation gets the chance multiplied once, the second twice, and so on, so 50% gives a chain of roughly seven generations and 25% roughly three. 100% is off. It only counts when a chain passes straight from one emitter to another: if a chain goes through one of your own objects in between — a puff that spawns smoke on its own death — that new emitter starts fresh at the full chance, since the plugin isn't involved in that creation.

Destroy when finished details: an emitter that has never emitted is left alone, and clearing particles never counts as finishing. Emitting manually with Auto start off does count as finishing, so turn this property off for an emitter you emit from repeatedly. Objects created by Spawn object are ordinary instances and are not destroyed with the emitter.

Particle Collision

Test particles against objects in the layout, so particles can hit things without any events. Collision is off by default and costs nothing until it is turned on.

PropertyDefaultWhat it does
Collision modeDisabledDisabled does nothing. All solids collides with any object that has the Solid behaviour, so it follows your layout automatically. Specific object type collides with the target below, which suits one-way collisions such as rain hitting water but not the ground.
Collision targetNoneThe object type or family particles collide with, used by the Specific object type mode. Pick a family to collide with several kinds of object at once.
Collide across layersNoAlso collide with objects on other layers, so particles can hit things you have separated onto their own layer. Costs a little more than same-layer collision, because it scans the target's instances instead of using collision cells.
Remove on collisionNoRemoves a particle as soon as it touches a collision target. A particle that stays inside an object is only removed once.
Spawn on collisionNoneCreates this object where a particle hits, such as a puff or splash. Independent of Remove on collision, so you can have one, the other, or both.

Collision details: particles are treated as points, and the test uses each object's collision polygon, so shapes and holes are respected but the particle is a single point rather than a circle. Removing a particle this way does not create the object set in Spawn object, which is only for particles that expire; use Spawn on collision for impacts. The object is created where the particle was when it hit, which is inside the target rather than exactly on its surface.

Because a particle is a point, a fast particle can pass through a thin object between two frames, and a particle that starts inside a solid object reports the collision as soon as it is tested. All solids looks for the Solid behaviour itself, so the Solid behaviour's collision filtering by instance tags is not applied: every enabled solid is a target.

About layers: by default only objects on the emitter's own layer are tested, which is what Construct does for most of its own collision checks. Turn on Collide across layers to test other layers too — handy when you keep things like the player and enemies on separate layers for drawing order.

Cross-layer collision follows what you see, not layout positions. The particle is carried through draw-surface co-ordinates into the target's layer before the test, the same route Construct's own cross-layer collision takes, so layers with a different scale, parallax or scroll still collide exactly where they appear to overlap. Layers that share a transform — the usual case for layers that only organise objects — skip the conversion entirely. There is also no extra cost when the option is off, and no cost at all while collision is disabled.

The one trade is how candidates are found: Construct's collision cells are indexed per layer, so with the option on the plugin scans the collision target's instances instead, as Construct itself does when layer transforms differ. With a very large number of instances of the target type, that scan is the part to watch.

Editor Display

How much the emitter draws in the Layout Editor. This has no effect at runtime.

PropertyDefaultWhat it does
ModeAdaptiveFull always draws everything: the marker, emission area, direction arrow, spread cone, representative particles, gravity arrow and a swirl badge when turbulence is on. Adaptive draws less as you zoom out. Minimal draws only the emitter marker, which suits background dressing.

The display also follows the instance's own Opacity, Colour and Blend mode, and the representative particles show a single frame when Enable atlasing is on, so the preview matches one particle rather than the whole image sheet.

Preset

Two links for moving a whole configuration in and out of an instance as JSON. Handy for sharing settings as text, and for pasting the presets that ship with ParticlesX.

PropertyDefaultWhat it does
Import preset JSON—Click Paste, paste the JSON and click OK. Every value that matches a property is applied to this instance, then a summary reports how many values were applied, anything the editor adjusted to fit a property's range, and anything it ignored. A preset can carry emission, movement, tint, size, opacity, rotation, animation, lifecycle and collision values, plus the instance's Blend mode.
Copy preset JSON—Click Copy to put this instance's current settings on the clipboard as preset JSON, ready to paste into another instance, a preset file, or a text editor.

A preset is a plain JSON object of property names to values:

``json { "emission-shape": 1, "shape-radius": 32, "speed": 159, "tint-start": "#c2d1f4", "blend": 1 } ``

Numbers and true/false are written as they are. Dropdowns can be written either as the item number (counting from 0, which is what Copy and the preset files use) or as the item text in quotes, for example "emission-shape": "Circle". Colours are "#rrggbb" strings. blend is the instance's own Blend mode: 0 is Normal and 1 is Additive.

Names this version does not recognise, values that do not fit their property, and the three Spawn object properties are ignored rather than guessed at, and the summary says so. Nothing in a preset is applied until you click OK, and properties you leave out keep their current values.

Values that already match are left alone, so pasting the same preset twice changes nothing. Each property that does change is added to the undo history, which means Ctrl+Z steps back through an import one property at a time — the same granularity as editing the properties by hand. Construct's addon API can only create undo points one property at a time, so a large preset takes several presses to undo. If that matters, copy the preset out with Copy preset JSON before importing over an effect you care about.

Triggers

TriggerFires when
On startThe emitter is started by the Start action or by restarting it. The start delay begins from this moment. An emitter that starts by itself is already started when it is created, which Construct cannot report as a trigger.
On stopThe emitter stops: by the Stop action, when a one-shot emitter releases its burst, or when the emission duration runs out. Particles already alive carry on.
On all particles deadThe last live particle expires. Clearing particles does not count.
On particle collidedA particle touches a collision target. Inside it, ParticleX and ParticleY give the particle's position, CollisionUID identifies the object that was hit, and Remove current particle drops the particle.
On particle collided withThe same, but only for collisions with the object type or family given in the parameter. Use it to react to particular targets, such as only enemies. This trigger does not pick the object that was hit: follow it with Pick instance by UID using CollisionUID, otherwise the event still runs with every instance of that object type picked.
On particle deadA particle reaches the end of its life. ParticleX and ParticleY give its position, and the object set in Spawn object is created afterwards as usual. Particles removed by a loop, by a collision or by clearing are not dying, so they do not fire this.

Rescaling an existing effect. Set Effect scale rather than editing half a dozen properties: 2 doubles the sizes, speeds, gravity and emission area together, and 0.5 halves them. Useful when the same preset has to work at two very different sizes, for example a handheld screen and a boss attack.

Continuous trail. Auto start on, Relative space, lifetime 0.5, speed 20, spread 10, fades out on, and Destroy when finished turned off (a trail should keep going).

Fire-and-forget effect. A self-contained effect needs no events at all: set a start delay of 0.5, an emission duration of 3, and leave Destroy when finished on. The emitter waits half a second, streams for three seconds, then cleans itself up once the last particle has faded. Use the Start action to run the same emitter again later, for example for a damaged engine that smokes for a few seconds after each hit.

Chains that fend for themselves. To make a firework that throws off smaller bursts, set Spawn object to the same emitter (or another preset) with a modest Spawn chance — and set Chain decay to around 50%. Each generation of spawned emitter is half as likely to spawn again as the one before, so the effect cascades for several generations and then naturally stops, with no events and no risk of a chain that grows without end.

Particles that affect the game. Add For each particle, then put your own conditions and actions underneath it. For example: For each particle → System Compare two values — distance(ParticlesX.ParticleX, ParticlesX.ParticleY, Player.X, Player.Y) < 16 → Player: subtract 1 from health, and ParticlesX Remove current particle. The same shape covers sparks that stick to a wall, embers that light a fuse one at a time, or particles that spawn a decal where they land.

Impacts with no events at all. Set Collision mode to All solids, turn on Remove on collision, and set Spawn on collision to a puff or decal object. Sparks now die where they land and leave a mark, entirely from properties — and because Destroy when finished still applies, the emitter cleans itself up once the last particle is gone.

Bullet-hell particles that interact. Give the emitter a collision target for the enemies (properties, or Add collision target if there is more than one kind), then add an On particle collided with (enemies) event: Pick instance by UID — ParticlesX.CollisionUID — Enemy: subtract 1 from health, and ParticlesX Remove current particle. The particle is the projectile, the pattern comes from the emitter's speed, direction and spread, and nothing needs to be a Sprite. Remember that collision targets added by the action stay until they are cleared, which is how an emitter can be re-used for a different job later.

Performance tips

  • Capacity is the main cost. Set it to roughly the number of particles you expect alive at once. Around 2000 particles per emitter is comfortable on desktop; a few hundred is plenty for most effects.
  • Big, overlapping, additive particles cost the most. That cost is fill rate, not particle count: it depends on how much of the screen the particles cover. If a glowing effect is slow, reduce the particle size or the emission rate before lowering capacity.
  • One emitter, one draw call. All particles from an emitter are drawn together, so a handful of emitters is cheap. Hundreds of emitters is not.
  • Turn on Destroy when finished for one-shot effects so finished emitters do not linger in memory.
  • Leave turbulence at 0 unless you need it. It is cheap, but it is the only optional feature that adds work for every particle, every frame.
  • An idle emitter costs nothing. While an emitter is not emitting and has no particles, it stops ticking until it is started or emits again, so background emitters that have finished are free to leave in the layout.
  • The object's box grows with its particles. The plugin resizes the emitter to cover the particles so they are not culled, and a bigger box means more of the layout is checked for collisions. Keep the emission area tight and Effect scale sensible rather than spreading one huge emitter over the whole layout.

Things to watch out for

  • Tints can only darken or colour, not brighten. If a tint seems to do nothing, the image is probably already dark. Use a light image, or Additive blending.
  • Tint alpha is ignored. Use the Particle Opacity group to fade particles.
  • A one-shot emitter fires when it is created if Auto start is on. To fire again, use the Start action, Restart emitter or Emit particles.
  • Clearing is not dying. Clear particles never triggers On all particles dead and never spawns objects.
  • On stop fires as soon as the emitter stops, not when the screen is clear. Use On all particles dead when you need the moment the last particle has gone.
  • A particle loop is a snapshot. For each particle visits only the particles that were alive when it started, and keeps visiting them even if something removes one mid-loop. The order of particles in the loop is not meaningful.
  • Removing a particle is not dying, but it still counts as the emitter running out. Remove current particle, Remove on collision and particle expiry never create the object set in Spawn object — that is only for particles that expire, and collisions have their own Spawn on collision. All of them, though, leave the emitter reporting On all particles dead and Destroy when finished normally. Clear particles is the exception: it is deliberate, so it never counts as finishing.
  • Collision triggers can run many times in one frame, once per particle that hits something. That is what makes bullet-hell patterns possible without Sprites, but keep the events inside them light when many particles are colliding at once. A particle that stays inside an object reports one collision, not one per frame.
  • On particle dead runs once per particle that expires, which with a high emission rate is a lot of events. It's there for full customisation — spawning your own objects, recording where particles fell, and so on — but Spawn object handles the common case without any events at all.
  • Cross-layer collisions follow what you see. With Collide across layers on, particles collide with objects where they appear, including on layers with a different scale or parallax. The trade is that it scans the target's instances each frame rather than using collision cells.
  • Effect scale multiplies property values, it does not replace them. Setting speed 200 on a 2× effect gives 400 pixels per second, and the Speed expression still reports 200. It also does not scale objects you spawn on death or on collision.
  • Particles are 2D. In a 3D scene they are drawn as flat quads, so they behave like Sprite objects and do not turn to face the camera.
  • The emitter's size and origin belong to the plugin while it has particles. The object is resized and its origin moved every tick so the bounding box covers the particles, and it is restored to the size you gave it once they have gone. Do not animate the emitter's Width, Height or origin, and do not rely on GetBoundingBox or Is on screen to describe the effect: use Effect scale to size the effect instead.
  • The instance opacity applies to the particles. Setting the emitter's Opacity, or changing it in a script, scales the opacity of every particle, on top of the Opacity group's own settings.
  • The instance time scale applies to the particles. Setting Time scale on the emitter, or in a script, slows, speeds up or pauses its particles along with its emission timings. Use it to pause one effect without pausing the game.
  • An object set in On particle collided with is not picked. See that trigger above: pair it with Pick instance by UID and CollisionUID, or the event will run with every instance of that object type still picked.
  • All solids ignores Solid collision filtering. All solids finds the Solid behaviour itself, so every enabled solid is a collision target regardless of the behaviour's tag filtering. Use Specific object type when you need to be picky.
  • Savegames restore the emitter's settings, not its particles. Loading a save keeps the rate, tints, gravity, collision targets and emission cycle that were set at runtime, so a spent one-shot stays spent and a stopped emitter stays stopped. The particles themselves are not saved: the effect simply continues with those settings, which is what one would expect of a transient visual.
